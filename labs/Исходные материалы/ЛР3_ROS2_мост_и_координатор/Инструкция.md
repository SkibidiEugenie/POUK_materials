# ЛР3. Инструкция: ROS 2, мост к стенду и координатор

Документы работы: [Задание](Задание.md) · **Инструкция** (этот файл) · [Шаблон отчёта](Шаблон_отчёта.md)

**Где что искать.** Теория — глава 3 пособия: данные-центричная модель и DDS (§3.2–3.3), QoS как контракт, правило совместимости и типовые профили (§3.4), физическое время и метки времени датчиков (§3.5.1–3.5.2), исполнители и группы обработчиков (§3.6), домены и выбор между топиком, сервисом и действием (§3.7), граница «ROS — не-ROS» и паттерн адаптера (§3.8); глава 4: плоский автомат и его рост (§4.3.1), иерархические автоматы (§4.3.2), протокол цели и идемпотентность (§4.4). Главы 5 (§5.3–5.4) — многомашинная конфигурация и время.

**Порядок работы.** Шаги 0–6 выполняются **на компьютере с виртуальным стендом**, без оборудования. На занятие бригада приходит с пройденными `check_bridge` и `check_coordinator`; у стенда выполняются шаги 7–9.

## 1. Архитектура развёртывания

```
 ПК (Ubuntu, ROS 2)                                  NanoPi-AR (ROS 2, тот же дистрибутив)
┌──────────────────────────────────────┐   сеть    ┌───────────────────────────────┐   UART    ┌──────────────┐
│ robot_state_publisher  ← URDF        │  DDS,     │ stand_bridge (pouk_bridge)    │  протокол │ OpenCM9.04   │
│ coordinator (pouk_coordinator)       │◄─────────►│   ├ pouk_link: канал ЛР2      │◄─────────►│ прошивка ЛР2 │
│ rviz2                                │  домен N  │   └ исполнитель траектории    │   v2      │ + 6 × AX-12A │
└──────────────────────────────────────┘           └───────────────────────────────┘           └──────────────┘
```

**Разделение забот** (§3.9, п. 3): мост — только коммуникация (топики ↔ протокол); кинематика — библиотека `pouk_link.kinematics` без ROS; автомат координатора — ядро `pouk_coordinator/fsm.py` без ROS; порт, частоты, имена суставов, пределы — параметры (`pouk_bringup/config/*.yaml`). Ядра проверяются модульными тестами без ROS — критерий приёмки §3.8.2.

**Виртуальный стенд** — тот же мост, подключённый вместо `/dev/ttyS1` к модели микроконтроллера `pouk_link.sim_mcu` по TCP. На модели работает всё, кроме физики: люфта, задержек реальной шины и реальных часов второй машины.

## 2. Подготовка

### Шаг 0. Рабочее место (дома)

1. **ROS 2 на ПК.** Ubuntu 22.04 + Humble или Ubuntu 24.04 + Jazzy (установка — docs.ros.org). **Дистрибутив ПК и NanoPi должен совпадать**: узлы разных дистрибутивов между собой не работают. Какой дистрибутив стоит на NanoPi, сообщает преподаватель.
2. Пакеты:

   ```bash
   sudo apt install python3-serial python3-pytest ros-$ROS_DISTRO-xacro ros-$ROS_DISTRO-robot-state-publisher \
        ros-$ROS_DISTRO-joint-state-publisher-gui ros-$ROS_DISTRO-control-msgs ros-$ROS_DISTRO-rqt-graph
   ```

3. Сборка и тесты:

   ```bash
   cd code/pouk_ws
   source /opt/ros/$ROS_DISTRO/setup.bash
   colcon build --symlink-install
   source install/setup.bash
   colcon test --event-handlers console_direct- ; colcon test-result --verbose | tail -30
   ```

   Падают тесты шагов 2 и 5 этой работы и шагов ЛР4-А — это нормально. Тесты `pouk_link` (ЛР2) обязаны проходить: мост работает поверх вашего канала.
4. **WSL2.** Если ROS 2 работает в WSL2 и топики не видны между терминалами, выполните во всех терминалах `export FASTDDS_BUILTIN_TRANSPORTS=SHM` и один раз `ros2 daemon stop`. Для шагов 7–9 (две машины) WSL2 не подходит — нужна Ubuntu на компьютере или виртуальная машина с сетевым мостом.

**Правило терминалов.** В каждом новом терминале: `source /opt/ros/$ROS_DISTRO/setup.bash && source code/pouk_ws/install/setup.bash` и одинаковый `export ROS_DOMAIN_ID=<номер бригады + 10>` — чтобы бригады в одной сети не видели узлы друг друга.

## 3. Базовый маршрут

### Шаг 1. Описание робота (дома)

```bash
ros2 launch pouk_description display.launch.py
```

В RViz — модель стенда; ползунки `joint_state_publisher_gui` поворачивают суставы. Проверьте знаки: положительный `joint2` наклоняет руку вперёд (+x), положительный `joint1` поворачивает от +x к +y. Тест `pouk_description/test/test_urdf_matches_kinematics.py` сверяет URDF с ОЗК и ПЗК приложения А: кончик схвата `tool0` приходит в точку, вычисленную `pouk_link.kinematics.ik`, с точностью до микрона. Если на шаге 0 ЛР1 вы измерили другие длины звеньев — поправьте их **одновременно** в `urdf/pouk_arm.urdf.xacro` и в `pouk_link/kinematics.py` и убедитесь, что тест проходит.

### Шаг 2. Суставы по именам (дома)

Реализуйте `JointMap.to_stand` в `pouk_bridge/pouk_bridge/joint_map.py` (блок `ЛР3-шаг2`). Правила:

- порядок имён в сообщении произволен: выборка — **по именам** через `self.index`;
- неизвестное имя — ошибка `JointMapError` (признак чужой конфигурации, молча игнорировать нельзя);
- суставы, которых нет в команде, берутся из `current`; если `current` не задан — ошибка со списком отсутствующих;
- калибровка: q_стенд = sign · q_ROS + offset.

Проверка: `colcon test --packages-select pouk_bridge` — проходят тесты `test_joint_map.py`.

**Калибровка своей сборки** — на стенде (шаг 9): если сустав движется в обратную сторону или ноль смещён, исправьте `joint_signs`/`joint_offsets` в `pouk_bringup/config/stand.yaml`, а не код.

### Шаг 3. Профили QoS (дома)

1. Реализуйте блок `ЛР3-шаг3` в `pouk_bridge/pouk_bridge/bridge_node.py`: три профиля — для состояния суставов, командного топика и режима стенда. Требования к ним записаны в комментарии блока; обоснование — по таблице §3.4.3 и правилу совместимости «запрошено ≤ предложено» (§3.4.1). Учтите, кто читает `joint_states`: `robot_state_publisher` подписывается с надёжной доставкой, координатор — с «регистровой» семантикой.
2. **Эксперимент «топик есть, данных нет».** Временно поставьте издателю `joint_states` `ReliabilityPolicy.BEST_EFFORT`, пересоберите и запустите виртуальный стенд с RViz (шаг 4). Модель в RViz не двигается, хотя `ros2 topic hz /joint_states` показывает 50 Гц. Диагностируйте **без перебора**:

   ```bash
   ros2 topic info -v /joint_states     # профили всех издателей и подписчиков
   ```

   В журнале `robot_state_publisher` ищите предупреждение о несовместимом QoS. Запишите в отчёт, что именно несовместимо и почему `ros2 topic hz` данные получал. Верните правильный профиль.
3. **Долговечность.** Сравните:

   ```bash
   ros2 topic echo --once /stand/state                                   # сразу печатает текущий режим
   ros2 topic echo --once --qos-durability volatile /stand/state         # ждёт следующей смены режима
   ```

   Объясните разницу через политику `DURABILITY` (§3.4.1).

### Шаг 4. Мост на виртуальном стенде (дома)

```bash
ros2 launch pouk_bringup sim_stand.launch.py                  # терминал 1: модель МК + мост + robot_state_publisher
ros2 run pouk_bringup check_bridge --lab3                      # терминал 2: самопроверка ЛР3
```

`check_bridge --lab3` проверяет режим стенда и его публикацию, имена суставов, частоту и метки времени `joint_states`, частичные команды, отказ на неизвестном имени и за пределом сустава, переключение `stand/hold`/`stand/run`. Без ключа `--lab3` добавляются проверки исполнителя траекторий — это ЛР4-А.

Посмотрите, что публикует мост:

```bash
ros2 node info /stand_bridge
ros2 topic echo --once /diagnostics            # счётчики канала (ЛР2) и микроконтроллера
ros2 topic pub --once /stand/joint_command sensor_msgs/msg/JointState "{name: [joint2], position: [0.3]}"
```

**Разрыв потока команд.** В диагностике найдите `mcu_max_cmd_gap_ms` — наибольший интервал между командами, который увидел микроконтроллер. Запустите `check_bridge` ещё раз (нагрузка на процесс моста) и сравните значение до и после, а также со значением приложения ЛР2 на том же компьютере. Мост — процесс Python, в котором поток передачи делит GIL с исполнителем ROS 2 (комментарий в `main()` моста): разрыв здесь больше, и T_wd из ЛР2 должен это выдерживать. Запишите цифры в отчёт.

### Шаг 5. Координатор (дома)

1. **Сначала диаграмма.** Нарисуйте диаграмму состояний координатора IDLE, HOMING, MOVE_POINT, CIRCLE, FAULT по событиям `home`, `move_to`, `circle`, `stop`, `reset`, `reached`, `done`, `fault` (описание — в документации `pouk_coordinator/fsm.py`). Для каждой пары «состояние × событие» решите: переход, самопереход или отказ с объяснением. Требования главы 4 (§4.8):
   - отказ достижим из **любого** состояния;
   - выход из отказа — только явный `reset`, и только если стенд готов;
   - повторный `home` во время наведения не перезапускает движение; повторный `move_to` в ту же точку не сбрасывает тайм-аут, в другую — заменяет цель.
2. **Таблица переходов.** Заполните `TRANSITIONS` в `pouk_coordinator/pouk_coordinator/fsm.py` (блок `ЛР3-шаг5`) по своей диаграмме.
3. `colcon test --packages-select pouk_coordinator` — тесты `test_fsm.py` проходят.
4. **Расширение варианта.** Нарисуйте диаграмму с расширением, посчитайте число дуг плоского автомата до и после (§4.3.1) и оцените, сколько дуг было бы в иерархическом варианте (§4.3.2). Реализуйте расширение в ядре `fsm.py` и узле `node.py`, добавьте модульные тесты расширения в `test_fsm.py`. Базовые тесты должны проходить без изменений.

### Шаг 7. Одноплатник (лабораторное занятие)

1. **ROS 2 на NanoPi.** Проверьте: `source /opt/ros/<дистрибутив>/setup.bash && ros2 --help`. Нужны пакеты `python3-serial` и `ros-<дистрибутив>-control-msgs`.
2. **Сборка только нужных пакетов** (одноплатнику с 512 МБ не нужны описание, координатор и MoveIt):

   ```bash
   cd <репозиторий>/code/pouk_ws
   colcon build --packages-select pouk_link pouk_bridge pouk_bringup
   source install/setup.bash
   ```

3. **Первый запуск вручную:**

   ```bash
   export ROS_DOMAIN_ID=<номер бригады + 10>
   ros2 launch pouk_bringup stand.launch.py
   ```

   Ожидаемо: `стенд на связи: HOLD, сессия МК …`. На реальном стенде RUN включает человек: `ros2 service call /stand/run std_srvs/srv/Trigger` — **при свободной рабочей зоне**.
4. **Служба systemd.** Остановите службу монитора ЛР2 (`sudo systemctl disable --now pouk-monitor.service`) — порт может принадлежать только одному процессу. Создайте `/etc/systemd/system/pouk-bridge.service`:

   ```ini
   [Unit]
   Description=POUK stand bridge (LR3)
   After=network-online.target
   Wants=network-online.target

   [Service]
   Type=simple
   User=<пользователь>
   Environment=ROS_DOMAIN_ID=<номер бригады + 10>
   ExecStart=/bin/bash -c 'source /opt/ros/<дистрибутив>/setup.bash && source /home/<пользователь>/<репозиторий>/code/pouk_ws/install/setup.bash && exec ros2 launch pouk_bringup stand.launch.py'
   KillSignal=SIGINT
   TimeoutStopSec=10
   Restart=on-failure
   RestartSec=3

   [Install]
   WantedBy=multi-user.target
   ```

   `KillSignal=SIGINT` — чтобы при остановке службы мост штатно перевёл МК в HOLD, а не оставил его срабатывать по сторожевому таймеру. Включите: `sudo systemctl daemon-reload && sudo systemctl enable --now pouk-bridge.service`; проверьте после перезагрузки: `journalctl -u pouk-bridge.service -n 30`.

### Шаг 8. Две машины (лабораторное занятие)

1. **Сеть и домен.** ПК и NanoPi — в одной подсети; одинаковый `ROS_DOMAIN_ID`; на Jazzy — `ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET` (значение по умолчанию); на Humble — не задан `ROS_LOCALHOST_ONLY=1`. Проверка групповой рассылки, на которой держится обнаружение:

   ```bash
   ros2 multicast receive          # на одной машине
   ros2 multicast send             # на другой
   ```

   Если пакет не пришёл — брандмауэр (`sudo ufw status`) или сеть без поддержки групповой рассылки. На ПК: `ros2 node list` показывает `/stand_bridge`.
2. **Время обнаружения.** Перезапустите службу моста и засеките по часам ПК, через сколько секунд `ros2 node list` увидит мост и через сколько придёт первое сообщение `joint_states`. Сравните с оценкой §3.3.2.
3. **Часы.** Смещение часов NanoPi относительно ПК:

   ```bash
   ros2 run pouk_bringup clock_probe server              # на NanoPi
   ros2 run pouk_bringup clock_probe client --n 50       # на ПК
   ```

   Программа печатает смещение θ по схеме NTP и его погрешность. У NanoPi нет часов реального времени с батарейкой: после включения без синхронизации время может отличаться на часы. Проверьте, работает ли синхронизация (`timedatectl`), при необходимости настройте NanoPi синхронизироваться с ПК (`chrony`) и повторите измерение.
4. **Влияние на метки времени.** Остановите синхронизацию на NanoPi (`sudo timedatectl set-ntp false` или, если используется chrony, `sudo systemctl stop chrony`) и сдвиньте его часы вперёд на 0,5 с: `sudo date -s "@$(python3 -c 'import time; print(time.time() + 0.5)')"`. Запустите на ПК `ros2 run pouk_bringup tf_audit` и посмотрите на RViz: что изменилось и почему (§3.5.2, §5.4.4)? Верните синхронизацию и убедитесь, что предупреждения исчезли.

### Шаг 9. Испытания на стенде (лабораторное занятие)

1. На ПК: `ros2 launch pouk_bringup lab3.launch.py` (без `sim`), на NanoPi мост работает службой.
2. **Калибровка.** Уменьшите `command_vmax` до 0,3 рад/с в `stand.yaml`, включите `stand/run` и подайте через `stand/joint_command` малые команды по одному суставу (±0,2 рад). Сравните направление движения манипулятора с моделью RViz и положение нуля с вертикальной сборкой. Исправьте `joint_signs`/`joint_offsets` при необходимости.
3. **Сценарий:** `home` → `move_to` точки варианта → `circle` варианта. Запишите `ros2 bag record /joint_states /coordinator/state /stand/state /diagnostics` — пригодится в отчёте и в ЛР4.
4. **Отказ:** во время `circle` остановите службу моста на NanoPi (`sudo systemctl stop pouk-bridge.service`) или оборвите связь, как в ЛР2. Координатор обязан перейти в FAULT с причиной; манипулятор — удерживать положение. Восстановите связь, выполните `stand/run` и `reset`, повторите сценарий.
5. **Расширение варианта** — на стенде.
6. Счётчики канала и `mcu_max_cmd_gap_ms` из `diagnostics` за весь прогон — в отчёт.

## 4. Задания со звёздочкой — подсказки

- **★1 действия.** Определите `.action` в `pouk_interfaces` (понадобится зависимость `action_msgs`); сервер действия в координаторе публикует обратную связь из `tick`; отмена переводит в IDLE с удержанием. Сравните поведение при вызове из двух клиентов одновременно.
- **★2 statechart/BT.** Для деревьев поведения на Python — `py_trees`; для statechart удобно выделить объемлющее состояние «движение» (HOMING, MOVE_POINT, CIRCLE) с общими дугами `stop` и `fault`.
- **★3 маркеры.** Текст — `Marker.TEXT_VIEW_FACING` в кадре `base_link` над манипулятором; цель — `Marker.SPHERE` в точке ПЗК уставки. Дисплей `MarkerArray` на топике `coordinator/markers` уже добавлен в конфигурацию RViz пакета описания.
- **★4 трафик.** `sudo tcpdump -i <интерфейс> -w discovery.pcap udp portrange 7400-7500` на NanoPi во время запуска ПК; в Wireshark — фильтр `rtps`.

## 5. Типовые ошибки

| Симптом | Вероятная причина | Что сделать |
|---|---|---|
| `ros2 node list` на ПК не видит мост | разные `ROS_DOMAIN_ID`; разные дистрибутивы; брандмауэр; нет групповой рассылки | сверить переменные; `ros2 multicast send/receive`; `sudo ufw disable` на время проверки |
| Узлы видны, `ros2 topic echo` молчит | несовместимые QoS (§3.4.1) | `ros2 topic info -v <топик>` |
| В RViz модель «прыгает» или предупреждения о будущем времени | часы NanoPi впереди ПК | `clock_probe`; синхронизация `chrony` |
| Мост падает при запуске: `NotImplementedError: ЛР3, шаг 3` | не выполнен шаг 3 | реализовать профили QoS |
| `check_bridge`: «частичная команда двигает только свой сустав» не проходит | выборка по индексам или `current` не учитывается | шаг 2, тесты `test_joint_map.py` |
| Стенд уходит в `WD_STOP` без видимой причины | разрыв потока команд моста больше T_wd | `mcu_max_cmd_gap_ms`; не запускать на NanoPi лишнего; пересмотреть T_wd (ЛР2, шаг 7) |
| Координатор сразу в FAULT «нет joint_states» | мост не запущен или другой домен; координатор подписан на другое имя топика | `ros2 topic list`; пространства имён в launch |
| `Permission denied: /dev/ttyS1` в службе | служба запущена от пользователя вне группы `dialout` | `User=` в службе; `groups <пользователь>` |
| Служба моста не стартует после перезагрузки | нет сети к моменту запуска или неверные пути `source` | `journalctl -u pouk-bridge.service`; абсолютные пути |

Обязательны: схема развёртывания и граф узлов, таблица QoS с обоснованием и разбор эксперимента «топик есть, данных нет», результаты `check_bridge` и `check_coordinator`, диаграмма и таблица переходов координатора с расширением варианта и подсчётом дуг, измерения смещения часов и времени обнаружения, протокол испытаний на стенде с отказом и восстановлением, сравнение разрыва потока команд моста и приложения ЛР2.
