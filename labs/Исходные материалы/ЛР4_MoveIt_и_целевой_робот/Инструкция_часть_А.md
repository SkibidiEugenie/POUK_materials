## 1. Как устроен контур

```
RViz: MotionPlanning ──► move_group ──► FollowJointTrajectory ──► stand_bridge ──► протокол v2 ──► OpenCM ──► приводы
      (цель, сцена)      (OMPL, ОЗК,     (действие                 (исполнитель:        (поток уставок
                          TOTG)           arm_controller/…)          интерполяция,        50 Гц)
                                                                     допуски, коды)
                 ◄───────────────────────────── joint_states (телеметрия МК, 50 Гц) ◄──────────────
```

Демонстрационный запуск, который генерирует MoveIt Setup Assistant (`demo.launch.py`), использует **фиктивное оборудование**: `joint_states` публикуются из плана, и манипулятор «всегда доезжает». Так был устроен контур 2025 года — мост просто пересылал план в порт. В этой работе состояние суставов — только из телеметрии микроконтроллера, а исполнитель на стороне моста отвечает за траекторию по контракту §4.5.4: либо гарантия выполнена, либо за ограниченное время отказ с кодом и удержание положения.

## 3. Базовый маршрут

### Шаг 1. Конфигурация MoveIt (дома)

1. **ОЗК.** В `kinematics.yaml` (блок `ЛР4А-шаг1`) задайте режим решателя KDL для пятизвенной руки. У руки пять степеней подвижности, а поза в пространстве — шесть чисел: без специального режима решатель ищет точную позицию **и** ориентацию и почти всегда отвечает «нет решения». Найдите параметр в документации плагина KDL и обоснуйте выбор в отчёте.
2. **Пределы.** В `joint_limits.yaml` (блок `ЛР4А-шаг1`) задайте для `joint1`…`joint5` `max_velocity` и `max_acceleration`. Скорость — не выше той, при которой привод отрабатывает уставки по времени с ошибкой в пределах допуска по пути (опирайтесь на измерение слежения ЛР2); ускорение — например, из условия разгона до `max_velocity` за 0,5 с. Без предела ускорения параметризация по времени в MoveIt 2 невозможна: объясните почему (§4.5.3).
3. Проверка: `colcon test --packages-select pouk_bringup` — тест `test_moveit_config_loads` теперь доходит до проверки описания исполнителя и падает на ней: это шаг 2.

Пределы положения суставов берутся из URDF — это те же целые миллирадианы, что в прошивке.

### Шаг 2. Описание исполнителя (дома)

В `moveit_controllers.yaml` (блок `ЛР4А-шаг2`) опишите контроллер `arm_controller`: тип `FollowJointTrajectory`, пространство имён действия, признак контроллера по умолчанию, список суставов. Имя действия, которое объявляет мост, — параметр `action_name` моста (`arm_controller/follow_joint_trajectory`). Тест `test_moveit_config_loads` проходит полностью.

Прочитайте секцию `trajectory_execution` того же файла: `allowed_start_tolerance` (насколько фактическое состояние может отличаться от начала плана) и `allowed_goal_duration_margin`. Как они согласуются с `start_tolerance` и `goal_time_tolerance` моста (`pouk_bringup/config/*.yaml`)?

### Шаг 3. Интерполяция (дома)

Реализуйте `Trajectory.sample` в `pouk_bridge/pouk_bridge/trajectory.py` (блок `ЛР4А-шаг3`). На отрезке [t₀; t₁] длительностью T, τ = t − t₀, h = q₁ − q₀:

- **линейная** (только положения): q(τ) = q₀ + h·τ/T;
- **кубическая эрмитова** (положения и скорости v₀, v₁): q(τ) = q₀ + v₀τ + c₂τ² + c₃τ³, где c₂ = (3h − (2v₀ + v₁)T)/T², c₃ = (−2h + (v₀ + v₁)T)/T³;
- **квинтическая** (положения, скорости, ускорения a₀, a₁): q(τ) = q₀ + v₀τ + (a₀/2)τ² + c₃τ³ + c₄τ⁴ + c₅τ⁵, коэффициенты c₃, c₄, c₅ выведите из шести граничных условий сами — вывод обязателен в отчёте.

Вернуть положение и скорость — производную того же полинома. Выбор способа уже сделан в конструкторе по содержимому сообщения (`self.kind`). Проверка: `test_trajectory.py` — тест граничных условий сверяет q и v в узлах и численную производную.

### Шаг 4. Контракт исполнителя (дома)

В `pouk_bridge/pouk_bridge/executor.py` два блока `ЛР4А-шаг4`:

1. **Проверка начала** в `start()`: если первая точка задана на момент 0, фактическое состояние обязано быть в пределах `start_tolerance` от неё, иначе `INVALID_GOAL` с указанием сустава. Если первая точка позже нуля — траектория доводит привод от фактического состояния (это уже сделано в `Trajectory`).
2. **Допуски** в `step()`:
   - пока t ≤ длительности: превышение допуска по пути любым суставом → `DONE`, `PATH_TOLERANCE_VIOLATED`, в сообщении — сустав и ошибка;
   - после длительности: все суставы в допуске по цели → `DONE`, `SUCCESSFUL`;
   - после длительности + допуска по времени без достижения цели → `DONE`, `GOAL_TOLERANCE_VIOLATED`;
   - иначе `RUNNING`.

Семантика значений допуска в сообщении цели (класс `Tolerances` уже реализован): больше 0 — значение, 0 — значение по умолчанию исполнителя, меньше 0 — не проверять. Проверка: `test_executor.py` — тесты используют модель привода с ограничением скорости и заклиниванием.

### Шаг 5. Семантика отказа (дома)

В `bridge_node.py`, метод `_finish` (блок `ЛР4А-шаг5`): при любом отказе — сначала удержание **измеренного** положения, затем статус цели. Исключение — вытеснение новой целью: удерживать нельзя, иначе новая траектория начнётся с рывка. Отмена клиентом завершается `canceled()`, всё остальное — `abort()`.

```bash
ros2 launch pouk_bringup sim_stand.launch.py                      # терминал 1
ros2 run pouk_bringup check_bridge                                 # терминал 2: все проверки, включая траектории
```

Затем проверка заклинивания (перезапустите терминал 1):

```bash
ros2 launch pouk_bringup sim_stand.launch.py stuck:=3@12           # сустав 3 заклинит на 12-й секунде модели
ros2 run pouk_bringup check_bridge --stuck
```

Ожидаемо: отказ `PATH_TOLERANCE_VIOLATED` **во время** движения и удержание положения. Посмотрите в журнале моста, какой способ интерполяции он выбрал для каждой траектории.

### Шаг 6. Контур MoveIt на модели (дома)

```bash
ros2 launch pouk_bringup lab4a.launch.py sim:=true
```

В RViz на панели MotionPlanning: группа `arm`; перетащите интерактивный маркер или выберите позу `ready` во вкладке Planning → Goal State; **Plan**, затем **Execute**. Проследите за журналом моста: число точек траектории, длительность, способ интерполяции (MoveIt передаёт скорости и ускорения — квинтическая). Кнопка **Stop** отменяет исполнение: мост удерживает положение.

Самопроверка для своего варианта (во втором терминале, RViz можно не закрывать):

```bash
ros2 run pouk_bringup check_moveit --variant <номер бригады>
```

### Шаг 7. Препятствие и перепланирование (дома)

1. Добавьте препятствие варианта в сцену (центр и размеры — из задания, в мм переведите в метры):

   ```bash
   ros2 run pouk_bringup add_obstacle --xyz 0.115 0 0.045 --size 0.05 0.05 0.08
   ```

   Препятствие появится в RViz (Scene Geometry). Убрать: `ros2 run pouk_bringup add_obstacle --remove`.
2. Переведите манипулятор в точку A варианта и спланируйте переход в точку B. Для задания цели в пространстве суставов вычислите углы ОЗК:

   ```bash
   python3 -c "from pouk_link import kinematics as K; print(K.ik(0.080, 0.089, 0.030))"
   ```

   и задайте их в RViz (вкладка Joints) или воспользуйтесь `check_moveit --variant N --plan-only`, которая делает то же автоматически.
3. Сравните план без препятствия и с ним (снимки RViz с траекторией, число точек, длительность). Объясните, почему прямой путь в пространстве суставов пересекает препятствие.
4. Задайте цель **внутри** препятствия: планировщик должен отказать (`check_moveit` печатает код). Объясните, почему отказывает планировщик, а не исполнитель (§4.6.3).

### Шаг 8. Контур на стенде (лабораторное занятие)

1. На NanoPi мост работает службой из ЛР3 (`pouk-bridge.service`). Убедитесь, что тег `lab4a` собран на NanoPi (`colcon build --packages-select pouk_link pouk_bridge pouk_bringup`) и служба перезапущена.
2. На ПК: `ros2 launch pouk_bringup lab4a.launch.py` (без `sim`), затем `ros2 service call /stand/run std_srvs/srv/Trigger` при свободной рабочей зоне.
3. Первые планы — с **Velocity Scaling 0,1** на панели MotionPlanning, затем увеличивайте.
4. Запись для отчёта:

   ```bash
   ros2 bag record /joint_states /display_planned_path /stand/state /diagnostics
   ```

### Шаг 9. Испытания (лабораторное занятие)

1. **A → B с препятствием варианта** — три исполнения; время плана и фактическое время до `SUCCESSFUL`; ошибка в конечной точке.
2. **Отказ по допуску пути.** Во время исполнения мягким предметом (не рукой!) остановите звено 2 или 3. Ожидаемо: `PATH_TOLERANCE_VIOLATED` в журнале моста и в RViz, удержание положения, никакого продолжения движения к цели после снятия упора.
3. **Отмена** кнопкой Stop — удержание положения.
4. **Вытеснение:** во время исполнения запланируйте и исполните другую цель — первая завершается как вытесненная, вторая исполняется без рывка.
5. `mcu_max_cmd_gap_ms`, `cmd_lost`, `telem_lost` из `diagnostics` за время испытаний — в протокол.

## 5. Типовые ошибки

| Симптом | Вероятная причина | Что сделать |
|---|---|---|
| Plan: «No IK solution» для любой позы | не задан режим ОЗК только по положению | шаг 1 |
| Plan успешен, Execute: «Unable to identify any set of controllers» | `moveit_controllers.yaml` не совпадает с суставами или именем действия | шаг 2; `ros2 action list` |
| Execute сразу `INVALID_GOAL`: «стенд в режиме HOLD» | стенд не в RUN | `ros2 service call /stand/run std_srvs/srv/Trigger` |
| Execute: «start point deviates from current robot state» | фактическое состояние отличается от начала плана больше `allowed_start_tolerance` | не двигайте стенд между Plan и Execute; проверьте статическую ошибку привода |
| Исполнение «рывками» | не реализована интерполяция (исполнитель прыгает к точкам) или скорости не передаются | шаг 3; журнал моста: способ интерполяции |
| Исполнение не завершается, MoveIt отменяет по тайм-ауту | `step()` не возвращает `DONE` | шаг 4; `test_executor.py` |
| `PATH_TOLERANCE_VIOLATED` на каждом плане | скорость плана выше возможностей привода; допуск меньше статической ошибки | уменьшить Velocity Scaling; пересмотреть пределы шага 1 и допуски моста |
| Цель внутри препятствия «исполняется» | препятствие не добавлено в сцену (другой домен, move_group не запущен) | Scene Geometry в RViz; `add_obstacle` печатает результат |
